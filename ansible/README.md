# ansible/

Node configuration: everything between a booted Ubuntu image and a node
`kubeadm` can use. Run through the `ansible-runner` container image, never from
a bare workstation shell — `make deploy-nodes`, `make deploy-cicd`,
`make deploy-cluster`.

```
inventory/lab/   hosts.yml is the single source of truth for names, addresses,
                 roles. group_vars/all/vars.yml holds every pinned version.
                 secrets.sops.yml sits alongside it, SOPS+age.
playbooks/       10-bootstrap-nodes → 20-cicd-host → 30-cluster, in that order.
roles/           common, docker, hardening, kube_prereqs, kube_control_plane,
                 kube_worker, runner_host.
files/           known_hosts, regenerated by `make known-hosts`.
```

The ordering these playbooks belong to is [docs/REBUILD.md](../docs/REBUILD.md).
Nothing here should be run because it looks next.

# Findings

Things learned against the running lab that would be expensive to re-learn.
Each was an inline comment in the file it belongs to until the pass before
build 0002 — see [docs/conventions.md](../docs/conventions.md) for why they live
here now.

## SSH

### The CA cutover, and why `main` is not a state a rebuild can start from

`hardening_ssh_retire_legacy_keys` was flipped `true` on 2026-08-28 as the final
step of Phase D, after three preconditions were all satisfied: the break-glass
key existed, `sign.sh` had been exercised for real against every node, and CI had
its own certificate-signing path (`bootstrap/ssh/sign-ci.sh`) so retiring
`ansible-console` would not strand it.

Every node's `authorized_keys` is now reconciled to **exactly**
`hardening_ssh_authorized_keys`, removing anything not listed — including
`mark-workstation`, `ansible-workstation` and `ansible-console`, all three, on
every node. SSH CA certificates are the only way in. Console's `group_vars`
overrides this to carry the one offline break-glass key that survives; every
other host keeps the empty default and has `authorized_keys` fully emptied.

Verified live: all four nodes reachable via a freshly signed `sign.sh`
certificate post-cutover, static-key SSH confirmed refused on the cluster nodes.

**Flipping it back to `false` does not restore the old keys.**
`hardening_ssh_authorized_keys` still governs what state gets reconciled to, and
the retired keypairs are no longer distributed to any node's `authorized_keys`
template. It would just stop enforcing the current (correct) state, letting it
drift.

**And it is wrong to start a from-scratch build from.** Both this and
`hardening_ssh_trust_ca` are `true` on `main` with an empty
`hardening_ssh_authorized_keys`, so the *first* `make deploy-nodes` of a rebuild
empties `authorized_keys` on `1972-master-1`, `1972-worker-1` and
`1972-worker-2` — removing the workstation keys cloud-init just installed — and
points `TrustedUserCAKeys` at `bootstrap/ssh/ca.pub`, the **previous** Vault's CA
public key. A rebuilt Vault runs `generate_signing_key=true` and produces a new
keypair, so the private half that could sign a usable certificate no longer
exists anywhere.

It fails *late*: the run that does it succeeds, because its own SSH connection is
already established. The next run — and every step of Phase B and C — cannot
connect. Only `1972-console-1` survives, via `break-glass.pub`.

Nothing in this role guards against it. The gate is
[REBUILD.md step 0.7](../docs/REBUILD.md), and the cutover is redone as Phase E.

## ufw

### Why the pod CIDR is an allowed source for the cluster ports

`hardening_ufw_cluster_sources` includes `kubernetes_pod_cidr` alongside
`lab_subnet`, for the **same-node hairpin**: a pod reaching a hostNetwork-backed
Service whose chosen backend is its *own* node.

That packet never leaves the box, so nothing masquerades it, and it arrives on
the veth still carrying the pod source IP — which `lab_subnet` does not match, so
ufw's default-deny ate it. Silently: Cilium has already handed off to the kernel
stack by that point, so `cilium monitor` shows a clean `-> stack` and no drop
event anywhere in the CNI.

`hubble-peer` is `internalTrafficPolicy: Local`, so it hits this path on every
single connection. The apiserver hits it for any pod scheduled onto the control
plane — which is what had CoreDNS wedged on `waiting for Kubernetes API` until a
restart happened to reschedule it onto a worker.

This grants pods no reach they did not already have: cross-node, pod traffic is
masqueraded to its node IP and so already matches `lab_subnet`. Verified on the
lab — a pod reaches 10250 and 2379 on any *other* node today and is refused only
on its own. This makes that consistent rather than scheduling-dependent. Node
isolation that actually matters (sshd) is a separate rule and is unaffected.

## sysctls

### rp_filter has to be split out, and cluster nodes need 0 on `all`

The kernel uses `max(conf.all.rp_filter, conf.<iface>.rp_filter)` rather than
letting the more specific value win. Cilium sets `rp_filter=0` on the lxc veths
and `cilium_host` it manages, but **a non-zero `all` silently promotes every one
of them to strict mode**, and strict mode drops any packet whose route back to
the source does not leave via the interface it arrived on.

Pod-to-node-IP traffic is exactly that shape: the packet lands on the pod's veth,
while the route back to the pod goes via `cilium_host`. The SYN is discarded with
no reply, no RST, and nothing logged in ufw or the CNI —
`TcpExtIPReversePathFilter` is the only counter that moves. Anything reaching a
hostNetwork-backed Service on its own node hits it: `hubble-peer` on every
connection, the apiserver for any pod scheduled onto the control plane.

Same conflict class as `ip_forward` (which is deliberately absent from
`hardening_sysctls` because `kube_prereqs` sets it to 1 on cluster nodes and
would fight this role), and worse in one respect: **it regresses a running
cluster**, so `make deploy-nodes` against a healthy node was enough to break pod
networking on it.

Cluster nodes get `0` on `all`, which removes the floor rather than disabling the
check — `eth0` still inherits `default=2` (loose mode), so the physical NIC stays
filtered while Cilium's own interfaces keep the `0` they require.

`net.ipv4.conf.default.accept_redirects` and its v6 pair are carried over from
`/etc/ufw/sysctl.conf`, which this role disables so `log_martians` actually
sticks.

## runner_host

### The runner image tag is read from version.txt, not repeated

`runner_host_image_tag` reads `images/gha-runner/version.txt`. It was a hardcoded
`1.0.2` and drifted the moment `version.txt` went to `1.1.0` (the vault CLI,
added for `bootstrap/ssh/sign-ci.sh`): the image built, scanned and promoted
correctly, but the runner stack stayed pinned to a tag that predated it, so
`deploy-nodes` ran on an image with no vault binary and failed with `vault CLI
not found in this image`. Nothing anywhere compared the two numbers.

A floating tag is not the answer either — the pin is deliberate, because an
unattended runner should not silently change underneath a job. One source, still
explicitly pinned.

Deliberately **not** `:stable`, unlike `ANSIBLE_RUNNER` in the Makefile: that one
is pulled fresh per invocation by a short-lived container, while this is a
long-lived stack whose containers are only recreated by an explicit
`make deploy-cicd` from the workstation.

### The vault-ci directory is not ~/.ssh, on purpose

`runner_host_vault_ci_dir` is bind-mounted read-only into the runner container
and holds the AppRole credentials `sign-ci.sh` authenticates with, plus a copy of
`ansible-console`'s **public** key for it to sign.

Deliberately not `/home/<admin_user>/.ssh`: that directory is not mounted into
the runner container and never should be. Signing needs the public half only, so
the private key stays out of the runner's reach entirely.

## Versions

### etcd is pinned because kubeadm's version map lags the release

kubeadm's `SupportedEtcdVersion` map holds at most three minors and is often not
updated before a release. At v1.37.0 it stops at minor 36, so kubeadm falls back
to `DefaultEtcdVersion` **with a warning** rather than failing. Pinning
`etcd_version` explicitly makes the version a decision rather than a fallback.

The pin also runs one patch ahead of kubeadm's default, both times it has been
set: `3.6.14-0` over `3.6.8-0` for the 1.36 build, `3.7.1-0` over `3.7.0-0` for
1.37. Take the patch fixes; Trivy-scan the image rather than trusting the
changelog.

Note that 1.36 → 1.37 carries an etcd *minor* bump (3.6 → 3.7) along with it.
That is only safe because a from-scratch build has no data to migrate.

### Cilium's version lives in three places and they must agree

`cilium_version` here is what `playbooks/30-cluster.yml` installs **pre-Argo**.
`cluster/cilium/values.yaml`'s `# chart:` line and
`cluster/argocd/applications/00-cilium.yaml`'s `targetRevision` are what Argo CD
adopts and reconciles.

PR #83 moved two of the three and left this one at `1.20.0`. On a running cluster
that is invisible — Argo had already converged the release — but a rebuild would
have installed 1.20.0 and then upgraded the CNI mid-build on the first sync.

### cilium_kube_proxy_replacement only matters for a from-scratch build

This var affects a fresh `kubeadm init` (the `kube_control_plane` role) and the
ansible-orchestrated Helm install task's one-time values — both dead code paths
once Argo CD exists and owns the cilium release. The value that actually drives
the live cluster is `cluster/cilium/values.yaml`'s own `kubeProxyReplacement`.

It is kept in sync here so a from-scratch rebuild starts in the same mode instead
of needing the migration (`make remove-kube-proxy`) re-run on a brand new
cluster.

## Inventory

### lab_domain is not templated into the cluster values

Node FQDN is `{{ inventory_hostname }}.{{ lab_domain }}`. The internal tool
hostnames in `cluster/*/values.yaml` — `argocd.`, `vault.`, `grafana.` — are
hand-written rather than templated from this var, so **a change here means
updating both places**, plus the Unbound host overrides on OPNsense
([docs/01-network-validation.md](../docs/01-network-validation.md)).

The zone is Cloudflare-hosted and used for both. None of these services have an
inbound internet path; DNS-01 only needs the zone resolvable, not reachable.

### cluster_oidc_issuer is a one-way door

Baked into the API server at `kubeadm init` and into every IAM role trust policy.
Changing it means rebuilding the control plane. No trailing slash — the `issuer`
field in the published discovery document must match it character for character.
Full sequence: [docs/06-aws-federation.md](../docs/06-aws-federation.md).

The AWS values here mirror `nineteenseventytwo-cloud/config/aws.json`, which is
the source of truth. If they disagree, every `AssumeRoleWithWebIdentity` call
fails with a message that does not mention URLs.
