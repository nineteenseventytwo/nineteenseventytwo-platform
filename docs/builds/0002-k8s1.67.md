# Build 0002 — Kubernetes 1.37 rebuild

**Dates:** 2026-09-03 → *(open)*
**Runbook followed:** [`docs/REBUILD.md`](../REBUILD.md) @ `3ff2a9a`
**Target versions:** k8s `1.37.0`, etcd `3.7.1-0`, Cilium `1.20.1`
**Outcome:** **Failed.** Full SSH lockout across all three cluster nodes
(`1972-master-1`, `1972-worker-1`, `1972-worker-2`) during Phase E, with no
CI or SSH path back in on any of them — recovery required pulling each SD
card and editing the filesystem directly. Abandoned rather than repaired in
place; [build 0003](0003-ssh-cutover-retry.md) restarts from imaging with the
root cause fixed in the runbook itself. Everything through Phase D (nodes,
CI/CD, Kubernetes 1.37.0, Argo CD fully synced) worked and is carried
forward as proven — this was a Phase E failure specifically, not a
whole-runbook one.

---

## Why this build

A full from-scratch rebuild of the four-Pi lab, both to test the kubeadm
1.36.4 -> 1.37.0 minor bump on hardware that costs nothing to re-image if it
goes wrong, and to rehearse `docs/REBUILD.md` end to end for the first time.
Build 0001 was never proven as a repeatable sequence -
[`05-migration.md`](../05-migration.md)'s definition of done and
[`plan/05`](../plan/05-provisioning-completion-plan.md)'s WP-6 both call for
this run, and it is the only thing that turns the README's "how do I rebuild
everything from nothing" into a claim rather than an assumption.

## What broke that the runbook did not predict

**The SSH CA cutover locked out every cluster node, permanently for CI, and
there was no way back in except physically pulling SD cards.** Two edits —
`hardening_ssh_retire_legacy_keys: false` and the new Vault CA's `ca.pub` —
were made and confirmed correct locally, but never pushed before triggering
`deploy-nodes`. CI checks out the pushed branch, not local disk, so it kept
running against the *old* committed state: the step-0.7 `true`/old-CA
combination that step 0.7's own text already warned about. That reconciled
`authorized_keys` to empty on `1972-master-1`/`1972-worker-1`/`1972-worker-2`
(a one-way ratchet — `1972-console-1` alone survives, via a group-scoped
break-glass override) and left `TrustedUserCAKeys` trusting a CA the current
Vault can no longer sign against. By the time the fix (PR #123) actually
merged, the damage was already done: the very `deploy-nodes` run that should
have delivered it needed SSH access to run at all, and none remained on
three of four hosts. Not obvious in the moment because each symptom read as
a plausible one-off (cert TTL, agent noise, a bad `-i` flag — see the
Deviations table's earlier rows) rather than as one root cause with two
independent blast radii.

**Where the fix landed:** [`docs/REBUILD.md`](../REBUILD.md#phase-e--identity)
Phase E now opens with an explicit, unmissable gate — commit and push before
any `deploy-nodes` run for every SSH-trust-affecting change, with this
build's exact failure quoted as the reason. Step 0.7's existing prose warning
was not enough on its own; the difference this time is a verification
command (`git log origin/main..HEAD`) attached directly to the step where the
mistake actually happens, not just a warning earlier in the document.
