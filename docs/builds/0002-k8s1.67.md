## Why this build

A full from-scratch rebuild of the four-Pi lab, both to test the kubeadm
1.36.4 -> 1.37.0 minor bump on hardware that costs nothing to re-image if it
goes wrong, and to rehearse `docs/REBUILD.md` end to end for the first time.
Build 0001 was never proven as a repeatable sequence -
[`05-migration.md`](../05-migration.md)'s definition of done and
[`plan/05`](../plan/05-provisioning-completion-plan.md)'s WP-6 both call for
this run, and it is the only thing that turns the README's "how do I rebuild
everything from nothing" into a claim rather than an assumption.

| 4.1 | `make bootstrap-argocd` installs Argo CD cleanly | **Real bug, first-contact.** `cluster/argocd/values.yaml`'s `server.httproute.enabled: true` (added in build 0001's Gateway cutover, PR #102) makes the chart render an `HTTPRoute`, but that CRD is normally installed *by* Argo CD itself at sync wave −30 — a from-scratch cluster has neither Argo CD nor the CRD yet. `helm install` failed outright: `no matches for kind "HTTPRoute" ... ensure CRDs are installed first`. Never caught before because build 0001 only ever ran `helm upgrade` against a cluster where the CRDs already existed from an earlier sync — #102's own values change was never exercised as a fresh install | Fixed in the Makefile: `bootstrap-argocd` now applies `cluster/gateway-api-crds/standard-install.yaml` with `kubectl apply --server-side` (required — the CRDs' schemas exceed the 262144-byte last-applied-configuration cap, same reason the CRDs' own Argo Application already uses `ServerSideApply=true`) *before* the `helm install`, mirroring the same adopt-don't-wait pattern already used for Cilium. Confirmed clean on retry: `STATUS: deployed`, no stuck release left behind by the first failed attempt |
| 4.2 | Wave −20 (Cilium) reaches `Synced/Healthy`, unblocking everything after it | **Second real bug, same root cause class as 4.1 — never exercised from empty.** `cilium`'s Application never settled: `hubble.tls.auto` (default method `helm`) generates `cilium-ca` and the two `hubble-*-certs` Secrets with fresh random bytes on every template render. Confirmed via controller logs — each sync genuinely succeeds (`phase: Succeeded`, all three secrets server-side applied), then ~12s later the next comparison finds a new diff against the newly-rendered random values and reverts to `OutOfSync`; `selfHeal` re-syncs, forever. App-level health read `Progressing` throughout even though the DaemonSet and Deployment were both fully healthy (3/3, 1/1) the entire time — this is what actually blocked every wave after −20, not a real infra problem | Fixed: added the three cert Secrets to `ignoreDifferences` in `00-cilium.yaml`, same pattern the file already used for the ansible-injected ConfigMap keys. [PR #116](https://github.com/nineteenseventytwo/nineteenseventytwo-platform/pull/116), pending merge — will confirm `cilium` reaches and *holds* `Synced/Healthy` once it lands |
| 4.2 | Wave 0 (metallb) reaches `Synced/Healthy` | **Third real bug, same class again.** `metallb-speaker` sat `ContainerCreating` on all three nodes forever: `secret "metallb-memberlist" not found`. That secret is generated *at runtime* by `metallb-controller`, not a chart template — but `metallb-controller` itself couldn't be scheduled: `FailedCreate: exceeded quota: infra-quota ... used: limits.memory=1Gi, limited: limits.memory=1Gi`. Traced to `cluster/metallb/values.yaml` setting `speaker.frr.enabled: false` (the old toggle) while chart 0.16.x's actual BGP backend is gated by a *separate*, top-level `frrk8s.enabled`, defaulting `true` regardless. An entire unwanted FRR/BGP DaemonSet (5 containers/pod, ~640Mi limits.memory) had been running the whole time — exactly what saturated the 1Gi quota before the controller's turn. `policy/21-resource-quotas.yaml`'s `infra-quota` for `metallb-system` (PR #106, merged the day *before* this rebuild) was sized against build 0001's already-converged steady state, so the real footprint was never exercised | Root-caused, not patched around: `frrk8s.enabled: false`. Verified via `helm template` that this removes the frr-k8s DaemonSet and statuscleaner Deployment entirely, leaving 512Mi total — no need to raise the quota. [PR #117](https://github.com/nineteenseventytwo/nineteenseventytwo-platform/pull/117), merged |
| 4.2 | Argo CD manual sync nudges (`kubectl patch application ... operation.sync`) actually prune/re-trigger | Two real gotchas with the exact pattern this repo's own Makefile uses (`argocd-sync`/`argocd-sync-wait`, and every manual nudge in this build's own log). (1) `operation.sync` doesn't inherit `syncPolicy.automated.prune` — a manual sync applies everything but silently *skips* pruning resources no longer in the desired manifest (`status: 'PruneSkipped', message: 'ignored (requires pruning)'`) unless `prune: true` is explicitly set on that same operation object. This is what actually delayed metallb's fix from taking effect — the stale `frr-k8s` DaemonSet kept the quota saturated for several extra minutes after the fix had already synced everything else. (2) a `kubectl patch --type merge` with *identical* content to what's already on `.operation` is a no-op — Kubernetes sees no diff, no new operation gets queued, `phase` and `message` just sit there looking like nothing happened | Always include `"prune":true` explicitly on a manual sync patch, not just `revision`. To force a genuinely fresh operation (not just re-apply the same one), clear `.operation` to `null` first, then set it again — or use `argocd.argoproj.io/refresh=hard` annotation when only a re-*comparison* is needed, not a re-sync (this is what actually cleared `platform-manifests`' stale `OutOfSync`, once its underlying resources already matched). Neither is currently documented anywhere in this repo — worth a note in `REBUILD.md` or `cluster/README.md` before the next build hits the same confusion |
| 4.2 | `longhorn-system`'s `infra-quota` (also PR #106) is also too tight for a from-scratch converge | **Fourth real bug, same class as metallb but no unwanted component to disable — everything blocked here is genuinely needed.** `vault-0` and both monitoring PVCs sat `Pending` forever (`unbound immediate PersistentVolumeClaims`). Traced through: every CSI sidecar (`csi-attacher`/`provisioner`/`resizer`/`snapshotter`) crash-looping on `context deadline exceeded` connecting to `unix:///csi/csi.sock`, because the `longhorn-csi-plugin` DaemonSet serving that socket had **zero pods**, not even scheduled — `FailedCreate: exceeded quota, requested: limits.memory=768Mi, used: limits.memory=4Gi, limited: limits.memory=4Gi`. None of longhorn's CSI containers carry explicit `resources` in `cluster/longhorn/values.yaml`, so all 16 already-running containers fall back to the namespace `LimitRange` default (256Mi each) — exactly 4Gi, the old hard cap, with nothing left for the plugin | Raised `limits.memory` 4Gi→8Gi, `requests.memory` 2Gi→3Gi, with the reasoning (and an explicit watch-item for `instance-manager` pods, which don't exist yet on this build precisely because this was blocking the chain that creates them) written into the file per its own stated norm. [PR #118](https://github.com/nineteenseventytwo/nineteenseventytwo-platform/pull/118), pending merge |
| 4.2 | `cilium-operator`'s Gateway API controller never picks up newly-installed CRDs without a restart | **Fifth finding — deterministic, not a fluke, will recur every from-scratch build.** `gateway`'s `GatewayClass` sat `Accepted: Unknown, "Waiting for controller"` indefinitely even after `metallb`/`cilium` were both fully healthy. `cilium-operator`'s own logs (from 07:17, its actual startup) showed `Required GatewayAPI resources are not found` — because Cilium is installed *pre-Argo* by `30-cluster.yml`, before the Gateway API CRDs exist (those land later, during `bootstrap-argocd`'s fix from PR #116). The operator's informers/watches for Gateway API types apparently never retry establishing themselves once the CRDs later appear — confirmed: pod was 49 minutes old, 0 restarts, still reporting the CRD-missing state from startup | `kubectl rollout restart deployment/cilium-operator` after `bootstrap-argocd` completes — confirmed via fresh logs: `Successfully reconciled GatewayClass`, `Successfully reconciled Gateway`. This is an *inherent* consequence of the pre-Argo/post-Argo install split (same shape as the CRD chicken-and-egg PR #116 already fixed for Argo CD's own chart), not something a values change can prevent — worth adding as an explicit step in `docs/REBUILD.md` Phase D, right after `bootstrap-argocd`, rather than rediscovering it every build |
| 4.2 | `argocd-application-controller` survives comparing the whole fleet in one pass | **Sixth finding, and the one that cost the most time to diagnose** — a `platform-policy` sync (≈100 resources: NetworkPolicy ×25+, CiliumNetworkPolicy ×20+, ResourceQuota/LimitRange ×14 each) sat `phase: Running` for several minutes with *zero* actual apply activity in the controller logs. Looked exactly like a wedged Argo CD; chased stale-operation-state and prune semantics (see the row above) before checking `kubectl -n argocd get pods` directly — `argocd-application-controller-0`, 3 restarts, `exitCode: 137, reason: OOMKilled`. `cluster/argocd/values.yaml`'s `controller.resources.limits.memory` was `1Gi`, set in build 0001's PR #25 against "11+ child Applications" — this build has 17, and `platform-policy` alone is far bigger than anything PR #25 was sized against. Every OOM-restart orphaned whatever sync was mid-flight, which is exactly what made this look like a hang rather than a crash — the actual failure was one `kubectl get pods` away from every place the investigation was actually happening | `limits.memory` 1Gi→2Gi, `requests.memory` 256Mi→384Mi. Raised `argocd`'s own `infra-quota` alongside it (1Gi/3Gi→1536Mi/4Gi) — the same trap as #117/#118 (bump a limit without the quota, trade an OOMKill for a quota rejection). [PR #119](https://github.com/nineteenseventytwo/nineteenseventytwo-platform/pull/119), pending merge. **Lesson for next time:** when an Argo CD sync looks stuck with no log activity, check `kubectl -n argocd get pods` for controller restarts *before* chasing operation-state theories |
| 4.2 | Longhorn `instance-manager` pods get created once volumes need them | **Seventh finding — a genuinely different shape from #117/#118/#119: an invalid pod spec, not a quota rejection.** After the longhorn quota and controller-memory fixes both landed and every other symptom cleared (CSI plugin running, all 5 PVCs `Bound`, quota comfortable), `vault-0` and every monitoring PVC-backed pod stayed stuck: `AttachVolume.Attach failed ... volume is currently in detached state with some un-schedulable replicas`, and **no `instance-manager` pod existed anywhere**. `longhorn-manager`'s own controller logs had the real reason: `Pod "instance-manager-..." is invalid: spec.containers[0].resources.requests: Invalid value: "400m": must be less than or equal to cpu limit of 200m` — then a 2-minute retry backoff, forever, always the same failure. `cluster/longhorn/values.yaml`'s `guaranteedInstanceManagerCPU: 10` makes `longhorn-manager` set an explicit 400m CPU *request* on every instance-manager pod, but instance-manager sets no CPU *limit* of its own — `policy/20-limitrange-default.yaml`'s `longhorn-system` entry fills that gap with `default.cpu: 200m`. A request above its own limit is invalid at admission, full stop; no amount of quota headroom or retrying was ever going to fix it. This setting has been `10` since early in build 0001 — nothing to conflict with until a `LimitRange` gave the unset limit a value for the first time (also PR #106) | `default.cpu` 200m→500m, real headroom above the 400m this setting computes at this node size. [PR #120](https://github.com/nineteenseventytwo/nineteenseventytwo-platform/pull/120), pending merge |
| Phase E | `deploy-nodes` picks up local fixes to `hardening/defaults/main.yml` and `bootstrap/ssh/ca.pub` | **Eighth finding — a process bug, not a config bug, and the most disruptive one this build.** After Vault's new `ssh-client-signer` CA was generated and `hardening_ssh_retire_legacy_keys` set back to `false` locally, `deploy-nodes` (CI, self-hosted runner) checked out `main` and ran against the *committed* state of both files — neither edit had been pushed. Two silent, compounding failures resulted: the committed `hardening_ssh_retire_legacy_keys: true` (the step-0.7 lockout state, itself only ever fixed locally — see the 1.3 row above) reconciled every node's `authorized_keys` down to just `break-glass` (a one-way ratchet — flipping the flag back does not restore the removed keys), and the committed `bootstrap/ssh/ca.pub` still held the *previous* Vault instance's CA, so `sshd`'s `TrustedUserCAKeys` trusted a different key than the one now signing certs. Cert auth and static-key auth both failed with a clean `Permission denied` on every node — looked like a single SSH regression, was actually two independent local-only fixes that never reached the branch CI runs against. Diagnosed via break-glass console access: `authorized_keys` content and `ssh-keygen -lf` on both the live `/etc/ssh/ca.pub` and the locally-committed one (`git show HEAD:bootstrap/ssh/ca.pub`) matched exactly, confirming CI ran the stale committed state, not a live-drift or Vault-side issue | Both files committed and pushed together (this PR) rather than left local — `deploy-nodes` re-run against them restores CA trust immediately; static-key access stays retired by design, matching Phase E's actual end state. **Lesson for next time:** a fix that only exists in the working tree is not a fix for anything CI drives — land SSH-trust-affecting changes the moment they're confirmed correct, not batched with unrelated work |
